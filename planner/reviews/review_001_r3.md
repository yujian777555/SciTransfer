## 2. Findings that materially change gate decisions

### P0 — hardcoded GIS timeout facts and result count

- `src/scitransfer/r3_eval.py` defines `TIMEOUT_SECONDS=300` and `evaluate_one()` runs the program with that default. The preflight also declares 300 seconds.
- `scripts/r3_finalize.py` **hardcodes** two entries `duration_s=601.3`, `Timeout after 600s`, `n_valid_pairs=2` instead of deriving them from immutable timed execution logs. `scripts/r3_cleanup.py` likewise sets `n_valid_pairs=2` directly.
- Final `results/round_001_r3_evaluation_matrix.csv` contains TWO extra rows with missing task/arm identifying fields and `NO_OUTPUT`. JSON has six entries; CSV has eight data rows. No adequate explicit provenance for a consistent count.
- These are **documentation/evidence integrity defects**, not a license to label events fabricated without checking actual logs. Require retrospective *erratum*, NOT backfilled timestamps or overwritten original evidence.

### P0 — scorer exception coercion

- `evaluate_one()` broadly catches `Exception` from the scorer and outputs `status=SUCCESS, score=0`. Both #85 arms hit `KeyError('argmax')`. This might match an upstream policy of assigning 0 for invalid outputs but is **not yet verified** against the protected original grading wrapper.
- This should be labeled `SCORER_EXCEPTION` with raw exception and `score=null` as the *validated direct-return score*, plus separately an `assumed_failure_score=0` only if specifically validated against upstream official score semantics.
- Don't promote exception-derived 0s to genuine scorer-returned values.

### P0 — hidden-gold access boundary

- `prepare_isolated_workdir()` creates a junction from `workdir/benchmark` to the entire protected benchmark tree, including `eval_programs/gold_results`. Candidate program has a potential read path to hidden evaluation material. The six committed candidate scripts do not obviously attempt to use it, but **the harness is not safe for rigorous future transfer trials**.
- Future interactive runs require a candidate-facing sandbox with task input datasets ONLY; the scorer should run in a separate trusted evaluation context. Freeze old data; don't retroactively claim stronger access isolation.

### P1 — paired information value

- Two tasks have numeric A/B result pairs only if exception-imputed 0s are included. Task #16 has two direct-return zeros (empty outputs), Task #85 has two scorer-exception fallback zeros, Task #21 is timeout/null.
- Thus `n_valid_pairs=2` is *not* equivalent to two fully validated direct-return pairs and does not support transfer benefits; even numerical pairs have 0/0 floor effects.
- In addition, the treatment is a fixed single-shot prompt, NOT a strategy learned from source-domain trajectories or multi-step scientific decision policy. Cross-domain transfer hypothesis has not been tested.

### P1 — reported test coverage vs full experimental safety

- 14 new tests include scorer fixture parity, directory separation and hash verification, but do not establish the strong gold-access wall, actual child-process tree cleanup, provenance of timeout values or independent checker of summarized CSV vs JSON.
- Direct scorer provenance `DIRECT_ORIGINAL_SCORER_MODIFIED_RUNNER` is correct as a method label. `official_evaluation=false` must remain.
